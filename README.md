# Pulse

Сервис мониторинга доступности сайтов и API. Техническое задание — [`docs/TZ.md`](docs/TZ.md),
правила разработки — [`docs/AGENTS.md`](docs/AGENTS.md).

## Локальный запуск

```bash
cp backend/.env.example backend/.env   # заполнить DEBUG=true, SECRET_KEY и т.д.
docker compose up -d --build           # PostgreSQL :5432, Redis :6379, миграции, Celery worker + beat

cd backend && uv sync && uv run python manage.py runserver   # API на :8000
cd frontend && nvm use && npm install && npm run dev         # UI на :5173
```

## Ключевые решения

### Аутентификация (A1)

**Выбор: JWT (access + refresh), а не сессии с CSRF.**

- Frontend и backend живут на разных доменах (статический хостинг + отдельный backend).
  Сессионная cookie в таком случае требует `SameSite=None; Secure`, настройки CSRF-токена
  между доменами и `credentials` в каждом запросе. Токен в заголовке `Authorization: Bearer`
  не отправляется браузером автоматически, поэтому CSRF-атака на API невозможна по построению.
- Тот же токен без изменений подходит для Swagger, скриптов и тестов.
- Недостаток JWT — нельзя мгновенно отозвать выданный токен. Он закрыт так:
  - **access** живёт 15 минут;
  - **refresh** живёт 7 дней и **ротируется**:
    при каждом `/refresh` старый токен попадает в blacklist (таблица в PostgreSQL),
    повторное использование украденного refresh возвращает 401;
  - **выход** (`/logout`) заносит refresh в blacklist; access истекает сам не позже чем через 15 минут.
- Пароли хешируются **Argon2** (`Argon2PasswordHasher`), проверяются стандартными валидаторами Django
  (длина, схожесть с email, словарь частых паролей, только цифры).
- Эндпоинты `/auth/*` ограничены по частоте (20 запросов в минуту с IP) —
  защита от перебора паролей.

| Метод | Путь                     | Доступ        | Ответ                         |
|-------|--------------------------|---------------|-------------------------------|
| POST  | `/api/v1/auth/register`  | все           | `201 {user, tokens}` / `422`  |
| POST  | `/api/v1/auth/login`     | все           | `200 {user, tokens}` / `401`  |
| POST  | `/api/v1/auth/refresh`   | все           | `200 {access, refresh}` / `401` |
| POST  | `/api/v1/auth/logout`    | авторизованные | `204` / `401`                |
| GET   | `/api/v1/auth/me`        | авторизованные | `200 {id, email, created_at}` |

Все ошибки возвращаются в едином формате:

```json
{"error": {"code": "validation_error", "message": "Некорректные данные", "fields": {"email": ["..."]}}}
```

### Мониторы (A2)

REST API `/api/v1/monitors` (JWT, пользователь видит и меняет только свои мониторы):

| Метод  | Путь                       | Ответ                        |
|--------|----------------------------|------------------------------|
| GET    | `/api/v1/monitors`         | `200` список с пагинацией    |
| POST   | `/api/v1/monitors`         | `201` / `422`                |
| GET    | `/api/v1/monitors/{id}`    | `200` / `404`                |
| PUT/PATCH | `/api/v1/monitors/{id}` | `200` / `404` / `422`        |
| DELETE | `/api/v1/monitors/{id}`    | `204` / `404`                |

- **Пагинация:** `?page=2&page_size=50` (по умолчанию 20, максимум 100) →
  `{"count", "next", "previous", "results"}`.
- **Фильтры:** `?status=DOWN&status=PENDING`, `?is_active=true`, `?is_public=false`.
- **Валидация** (ошибки — `422` с разбивкой по полям):
  - URL только `http`/`https`;
  - интервал 60–3600 с;
  - таймаут 1–60 с и строго меньше интервала (при `PATCH` сверяется с сохранённым интервалом);
  - ожидаемый код ответа — диапазон `expected_status_from..expected_status_to` (по умолчанию 200–299);
  - не больше 20 мониторов на пользователя (`monitor_limit_reached`). Проверка квоты идёт под
    блокировкой строки пользователя (`SELECT ... FOR UPDATE`), поэтому параллельные запросы не
    создадут 21-й монитор.
- Те же ограничения продублированы `CHECK`-констрейнтами в PostgreSQL.
- Чужой монитор отдаёт `404`, а не `403`, чтобы не раскрывать факт его существования.
- Выключение (`is_active=false`) переводит монитор в `PAUSED`; включение — в `PENDING`
  со сбросом счётчика неудач и немедленной проверкой.

### Фоновые проверки (A3)

**Выбран вариант 1: Celery worker + Celery beat** рядом с веб-приложением.

- Celery уже нужен проекту и для других фоновых задач: AI-сводки по инцидентам (E1), очистка истории
  батчами (A7), повторная отправка уведомлений в Telegram (D2). Внешний cron покрыл бы только проверки.
- Проверки не зависят от HTTP-запросов пользователей: beat каждые **15 с** ставит задачу
  `checks.dispatch_due_checks`, она выбирает мониторы, у которых наступил `next_check_at`, и ставит
  по одной задаче `checks.run_check` на монитор.
- Worker работает с пулом потоков (`--pool=threads --concurrency=20`): проверки упираются в сеть,
  а не в CPU, поэтому зависший сайт не блокирует целый процесс.

**Как исключены двойные проверки:**

1. Выбор мониторов идёт в транзакции через `SELECT ... FOR UPDATE SKIP LOCKED`. В той же транзакции
   `next_check_at` сдвигается на интервал вперёд, поэтому второй планировщик (два тика одновременно
   или два процесса beat) либо пропускает заблокированные строки, либо видит, что монитор уже
   не просрочен. Это покрыто тестом с двумя параллельными транзакциями.
2. Повторная доставка той же задачи брокером (`acks_late`) отсекается блокировкой в Redis
   (`cache.add` — атомарная операция) на время проверки.

**Холодный старт и засыпание хостинга:**

- Следующая проверка считается **от текущего момента**, а не от пропущенного слота: монитор,
  проспавший 5 часов, проверяется один раз, а не 300.
- Задача в очереди живёт не дольше интервала монитора (`expires`): если worker был недоступен,
  устаревшие задачи брокер отбрасывает, и после пробуждения лавины нет.
- За один тик берётся не больше 100 мониторов (сначала самые просроченные).
- Защита от ложных инцидентов после простоя — см. раздел «Инциденты (A4)».

**Каждая проверка:**

- HTTP-запрос с таймаутом монитора, причём таймаут ограничивает и **общее** время чтения ответа,
  а не только ожидание отдельного пакета;
- не больше 5 редиректов;
- тело читается потоком и обрывается после 1 МБ, большой ответ не скачивается целиком;
- результат пишется в `check_results`: время проверки, успех, код ответа, время ответа, код ошибки
  (`TIMEOUT`, `DNS_ERROR`, `CONNECTION_ERROR`, `SSL_ERROR`, `UNEXPECTED_STATUS`,
  `TOO_MANY_REDIRECTS`, `BODY_TOO_LARGE`, `INVALID_URL`) и понятный текст причины на русском.

### Инциденты (A4)

Машина состояний монитора (`incidents.MonitorStateService`) применяется к каждому результату
проверки в одной транзакции с записью в `check_results`:

| Событие | Результат |
|---|---|
| успешная проверка | `UP`, счётчик неудач сброшен; открытый инцидент закрывается, длительность фиксируется в `duration_sec` |
| 1-я неудача подряд | статус не меняется, `consecutive_failures = 1`, запоминается `failing_since` |
| 2-я неудача подряд | `DOWN`, открывается инцидент с `started_at = failing_since` (начало простоя — первая неудача) |
| 3-я и далее | счётчик растёт, новый инцидент не открывается |

**Как исключены дубликаты открытых инцидентов:**

1. Обработка результата идёт под блокировкой строки монитора (`SELECT ... FOR UPDATE`):
   параллельные результаты одного монитора применяются строго по очереди. Это покрыто тестом
   с двумя одновременными неудачами из разных потоков.
2. В PostgreSQL стоит частичный уникальный индекс `UNIQUE (monitor_id) WHERE resolved_at IS NULL`.
   Даже при ошибке в коде второй открытый инцидент база не примет.

**Без ложных инцидентов:**

- «Мигающий» монитор (сбой, успех, сбой…) не открывает инцидент: нужны 2 неудачи **подряд**.
- Если между проверками прошло больше `2 × интервал + 60 с` (хостинг спал, worker был недоступен),
  неудача до перерыва и неудача после него не считаются подряд идущими: счётчик начинается заново.
- Опоздавший результат более старой проверки игнорируется и не откатывает состояние.
- Если монитор поставили на паузу во время проверки, её результат не меняет статус.

API (только чтение, только свои мониторы): `GET /api/v1/incidents?monitor={id}&is_open=true`,
`GET /api/v1/incidents/{id}`.
